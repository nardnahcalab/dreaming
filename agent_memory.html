◆ Dream Memory · Agent Integration

Putting crystallized memory
inside the agent

The dreaming pipeline distils 53 sessions into curated memory. That memory is only useful if the agent actually sees it. This is how it reaches OpenCode, Claude Code, Codex and Hermes — on demand through custom tool calls, and always-on through a bounded digest — with no cloud calls and no idle token cost.

01 The problem

Crystallized memory exists on disk. The agent's context window does not.

A dream pass turns raw transcripts into a compact set of memories — facts, preferences, projects, lessons, tasks. But an agent starting a fresh session has no idea those memories exist. It re-derives the user's preferences from scratch every time, burning tokens and arriving at a less accurate answer than the one already sitting on disk.

The obvious fix — dump everything into the system prompt — fails on cost. Full crystallized memory is unbounded; it grows with every dream, and the episodic layer beneath it holds 2,391 messages. Neither belongs in every prompt.

Design tension The facts an agent needs on every turn must already be in context. The facts it needs sometimes must cost nothing until asked for. One mechanism cannot do both — so there are two.

02 Two prongs

Complementary by design: depth on demand, breadth always on.

A · MCP tool calls

0 tokens when idle

A stdlib MCP server exposing three tools over stdio. The model decides when to search, so deep recall costs only what it returns.

  • dream_recall — crystallized search, optionally with episodic evidence
  • dream_status — what is in memory right now
  • dream_remember — write a durable memory back
  • Reaches the episodic layer, which the digest never does

B · Always-on digest

~2 KB, every session

A bounded, generated summary written into the memory file each agent already loads into its system prompt. No tool call required.

  • Hermes MEMORY.md + USER.md
  • Claude Code CLAUDE.md · Codex AGENTS.md
  • Managed block — regeneration never touches your own notes
  • Category split: preferences go to the profile, rest to notes

How a memory travels

Layer 1
Episodic transcripts

Append-only sessions from all four tools. Never modified.

Consolidation
Dream pass

LLM via DEH, heuristic fallback. New immutable artifact.

Layer 2
Crystallized memory

Curated entries with importance, confidence, provenance.

Delivery
MCP tools + digest

On-demand search, and a bounded block in every agent's prompt.

03 The MCP server

dream_memory/mcp_server.py — newline-delimited JSON-RPC 2.0 over stdio.

Written against the protocol directly, in the Python standard library — no mcp SDK, no install step, no dependency for any of the four hosts. The registered command is always python3 <abs>/dream.py mcp, so the server runs on exactly the same code as the rest of the pipeline.

Transport contract stdout is the protocol channel. Every log line goes to stderr, or the client sees a malformed frame and drops the connection. The test suite asserts stdout contains nothing but JSON lines.

Tools

ToolAccessBehaviour
dream_recall(query, limit, include_episodic) read Crystallized first (score = overlap + 0.3 × importance), episodic beneath as evidence when requested, pending write-backs surfaced explicitly.
dream_status() read Session/message counts by tool, latest dream, category breakdown, pending inbox, digest path.
dream_remember(content, category, importance, confidence, agent) write Appends to the inbox and regenerates digests immediately — the memory is live before any dream runs.

Protocol

# client → server
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "protocolVersion":"2025-06-18","capabilities":{},
  "clientInfo":{"name":"opencode","version":"2.4.1"}}}

# server → client  (instructions are injected into OpenCode's system prompt)
{"jsonrpc":"2.0","id":1,"result":{
  "protocolVersion":"2025-06-18",
  "capabilities":{"tools":{"listChanged":false}},
  "serverInfo":{"name":"dream-memory","version":"1.0.0"},
  "instructions":"Crystallized memory ... call dream_recall before
                 re-deriving user preferences ..."}}

Speaks 2024-11-05 through 2025-11-25, echoing the client's proposal. Tool failures return isError: true results — the model sees the message instead of the session tearing down — while an unknown tool name returns JSON-RPC -32602, which is what the spec requires.

04 The always-on digest

dream_memory/context.py — bounded, generated, managed.

Waiting for the model to decide to call a tool means paying the re-derivation cost instead. Preferences and project shape belong in the prompt from turn one. The digest writes exactly those, within a hard budget.

Targets and budgets

Hermes MEMORY.md 1400 ch
Hermes USER.md 900 ch
Claude CLAUDE.md 2000 ch
Codex AGENTS.md 2000 ch

Entries are sorted by importance then confidence, deduplicated, and packed until the budget is hit. Hermes keeps two files with genuinely different jobs — preferences → USER.md (who the user is), everything else → MEMORY.md (agent notes). Single-file targets receive the combined digest under one header.

Managed blocks

# markdown targets — CLAUDE.md, AGENTS.md
<!-- BEGIN dream-memory:managed -->
Auto-generated by `dream.py context` from crystallized memory.
Do not edit -- it is rewritten on every regeneration.
- (preference, imp=0.7) User prefers an open-source stack ...
<!-- END dream-memory:managed -->

# Hermes targets — written as exactly ONE real entry
[dream-memory:managed]
...
[/dream-memory:managed]
# separated from other entries by the literal "\n§\n"
Why the § delimiter matters Hermes parses MEMORY.md and USER.md by splitting on the literal "\n§\n" and re-joins with the same delimiter every time its own memory tool writes. A plain newline would let Hermes merge our block into one of its entries permanently. So the block is written as a real entry, and never contains the delimiter itself.

05 Write-back loop

dream_memory/inbox.py — agents contribute, the dreamer decides.

Agent
dream_remember(…)

An agent notices a durable fact, preference or lesson.

Append
inbox.jsonl

Write-once JSONL. Never rewritten, never deleted.

Next dream
joins prior entries

Normal keep / revise / drop rule applies, with provenance.

Result
ordinary crystallized entry

sources=[rem-…] records that an agent, not a transcript, said it.

Consumption is tracked by unioning inbox_ids across all dreams — the same pattern as processed_hashes. A consumed record is marked, never deleted, so the append-only invariant holds for the inbox too. Pending records are visible to recall and in the digest before any dream runs.

Hermes also gets the digest

Hermes injects MEMORY.md and USER.md into its system prompt as a frozen snapshot with a hard 2,200 and 1,375 character cap. The digests are budgeted beneath those limits (1400 / 900), and Hermes threat-scans entries at snapshot time — the digest is plain prose, so it passes.

07 Safety

Writing into files the user already owns demands more care than writing our own.

GUARD 01
Root isolation

A non-default memory root writes only the canonical digest. Agent files are untouched unless DREAM_DIGEST_FORCE=1 or DREAM_DIGEST_HOME relocates them.

GUARD 02
Never truncate

If a computed result would empty a file that had content, the write is skipped entirely (skipped_empty).

GUARD 03
Rolling backup

Every digest write first saves the previous content to <file>.dream-bak — one generation of recovery, never a pile of files.

GUARD 04
Marker-bounded edits

Only text between our markers is replaced. Foreign text in the same entry is preserved; an empty result falls back to the original.

GUARD 05
Degenerate output rejected

Placeholder replies ("content": "…") are filtered before they can reach crystallized memory or a digest.

GUARD 06
Episodic stays read-only

The MCP server exposes no write path to Layer 1. Write-back goes to the separate append-only inbox.

⚠ Incident: two data-loss bugs found during implementation

Both were caught before commit, both changed the design, both now have regression tests.

  1. Hermes profile wiped. An earlier upsert dropped any entry containing our markers wholesale. Because a previous generation had merged the user's own 717-byte profile into the same entry, the filter deleted it too. Recovered byte-exact from a transcript copy, then the parser was changed to strip only marker-bounded text.
  2. Scratch root overwrote live agent files. The isolation guard checked only the DREAM_ROOT environment variable, so dream.py --root /tmp/… bypassed it and wrote a test digest into the real CLAUDE.md, AGENTS.md and MEMORY.md. All restored from .dream-bak.
Fix: the guard now evaluates the actual root argument, not an environment variable; a non-default root can never reach agent files without an explicit opt-in. Both bugs are pinned by tests 10 and 11 in test_memory_context.py.

08 Runbook

Everything is local. Nothing here calls a cloud service.

# one-time: register with all four agents (Hermes YAML backed up first)
python3 dream.py connect

# regenerate the always-on digest by hand
python3 dream.py context

# see what agents have written back
python3 dream.py inbox

# run the server manually (what the agents spawn)
python3 dream.py mcp

# full cycle: ingest → dream → refresh digests → eval
./run_dream.sh

# tests
python3 test_memory_context.py     # 14 groups: digest, inbox, guards

# budget overrides
DREAM_DIGEST_MEMORY_CHARS=1400 DREAM_DIGEST_USER_CHARS=900 \
DREAM_DIGEST_CHARS=2000 python3 dream.py context
