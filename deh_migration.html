01Why migrate

Ollama was a fine stand-in while the pipeline was being proven. DEH is the production path on this box: hardware-validated configurations, a Docker flow the platform already manages, and an official SDK/CLI instead of an undocumented local daemon.

Hardware validated

✓GB10-native configs

meta-models/Muse-Glimmer-30B is published against dell-pro-max-gb10 — the exact platform of this machine. Container tags, GPU count and token limits are tested by Dell, not guessed.

Docker flow

▤Image already local

enterprise-dell-inference-meta-models-muse-glimmer-30b-gb10:latest (28.7 GB) is already pulled. Weights are fetched from the Hub at first boot via HF_TOKEN, so cold start is a download, not an image pull.

SDK + CLI

⚙One client, two surfaces

The Python SDK (dell_ai) discovers the live endpoint from inside dream_memory; the dell-ai CLI runs deploy / status / undeploy from the shell. Same underlying client, no drift.

OpenAI wire

⇄Standard protocol

SGLang speaks the OpenAI contract — /v1/chat/completions, /v1/models, /health. The client becomes portable: any OpenAI-compatible server can serve dreams later.

Removed

✕Ollama is gone

The LocalLLM class, /api/tags, /api/chat, format:"json" and the localhost:11434 default are deleted outright — not kept as a fallback.

Unchanged

⛨Safety net survives

The deterministic heuristic consolidator remains the last rung. If DEH is unreachable the pipeline still completes a dream instead of failing — same behaviour as before.

02Request flow after the swap

Requests travel along the top lane, responses return along the bottom lane. Discovery and operations enter from above and below. Watch the dashes — they trace the exact order the code executes.

prompt / response — OpenAI wire calls
information — weights & deployment config
intelligence — crystallized memory entries
Discovery is a separate concern. Before any arrow fires, the client resolves where the endpoint is: DREAM_DEH_ENDPOINT → dell_ai.deployments.list_deployments() → a direct docker ps scan. Only if all three miss does the heuristic run.

class LocalLLM:
    def available(self):
        urlopen("/api/tags", timeout=5)

    def chat(self, system, prompt, temperature=0.2):
        body = {
            "model": self.model,          # gpt-oss:20b
            "format": "json",             # ollama dialect
            "options": {"temperature": temperature},
            "messages": [...],
        }
        POST("/api/chat")
        return resp["message"]["content"]
dream_memory/deh.py — after
class DEHLLM:
    def available(self):
        GET("/health") or GET("/v1/models")

    def chat(self, system, prompt, temperature=0.2):
        body = {
            "model": self.model,          # from /v1/models
            "response_format": {"type": "json_object"},
            "temperature": temperature,
            "messages": [...],
        }
        POST("/v1/chat/completions")
        return resp["choices"][0]["message"]["content"]
Prompt text is untouched. DREAM_SYSTEM, the update rule, the 120 K adaptive budget and _extract_json() all carry over unchanged — only the transport and the envelope change. Dream artifacts stay byte-compatible, so eval still compares dream-0002 against the new dream correctly.

04Endpoint discovery ladder

The single riskiest part of the swap is finding the port. DEH's own registry helper parses 0.0.0.0:PORT->, but this box's live container binds 127.0.0.1:8080 — so the helper returns None. The client therefore walks four rungs and verifies each candidate before trusting it.

Explicit override — DREAM_DEH_ENDPOINT

Wins unconditionally. Used for tests, remote endpoints and pinning one deployment when several are running.

dell_ai.deployments.list_deployments()

Merges the JSON registry with live Docker discovery. Prefer the entry whose image slug matches the configured model (muse-glimmer), because app containers such as laya-deh also match the DEH image prefix but expose no chat routes.

Direct docker ps scan

Fallback when the SDK is not importable. Port regex accepts 127.0.0.1, 0.0.0.0 and [::] — the case DEH's own parser misses on this machine.

Verify with GET /v1/models

Every candidate is probed before use. A 404 or empty data[] rejects it, so an app container can never be mistaken for an inference endpoint.

App ≠ model. The running laya-deh container answers GET /v1/models but returns 404 on POST /v1/chat/completions. Discovery must filter on the configured model slug and verify chat capability, or the dreamer will bind to a dead endpoint.

05Ops runbook — CLI

Deployment is an operations concern, not a pipeline concern. The CLI owns the lifecycle; the SDK only reads the resulting endpoint.

# 1 — install once (project venv; system pip is externally managed)
$ uv venv .venv
$ uv pip install --python .venv/bin/python dell-ai
+ dell-ai==1.1.0
# 2 — authenticate with your Hugging Face token
$ .venv/bin/dell-ai login --token "$HF_TOKEN"
$ .venv/bin/dell-ai whoami
Status: Logged in
User: balaatdell
# 3 — deploy the dream model on this platform
$ .venv/bin/dell-ai models deploy \
    --model-id meta-models/Muse-Glimmer-30B \
    --platform-id dell-pro-max-gb10 \
    --engine docker \
    --gpus 1
→ fetches validated config, runs container, records endpoint
# 4 — verify the endpoint before dreaming
$ .venv/bin/dell-ai status
$ curl -s http://localhost:<port>/v1/models
{"data":[{"id":"meta-models/Muse-Glimmer-30B", ...}]}
$ .venv/bin/python dream.py dream
# 5 — tear down when done
$ .venv/bin/dell-ai models undeploy -d <deployment-id>
deployment id comes from `dell-ai status`
Cold start cost. The image is local (28.7 GB) but contains_weights: false — first boot pulls weights from the Hub. Expect minutes on the initial run and seconds thereafter. /health flipping to {"status":"ok"} is the readiness signal the client waits on.

07Failure modes

Every degradation path ends in a completed dream, never a crash. That contract predates the migration and is preserved exactly.

ConditionDetectionBehaviour
dell-ai not installedImportError on SDK Skip rung 2, fall through to docker ps scan
Registry misses 127.0.0.1 bindendpoint is None Own port parser handles loopback and IPv6 binds
Only an app container is runningchat route returns 404 Candidate rejected; no chat routes → no binding
No DEH container at allall four rungs miss available() false → heuristic consolidator runs
Server rejects response_formatHTTP 4xx Retry once without it; _extract_json() still strips fences/prose
Container up, weights still loadingtimeout / 503 Chat raises → dream falls back to heuristic; artifact still written
Model id mismatchserver 400 "unknown model" Client re-reads /v1/models and uses data[0].id
Invariant: dream.py dream always writes dream-NNNN.json. Engine availability changes quality of extraction, never the success of the pass — which is exactly why eval can keep measuring retention across the migration boundary.
